# 跨境物流轨迹查询网站 - 需求分析与技术规划

## Context

为跨境电商卖家和货代公司（B端）构建一个免费+增值付费的物流轨迹查询网站。用户可通过运输单号查询全渠道（国际快递、跨境专线、邮政小包、海运/空运）的物流轨迹信息。支持中英文双语，第一版即交付完整功能。

## 一、数据来源

### 1.1 混合数据架构（聚合 API + 直连承运商 API）

```
                    ┌─────────────────────┐
                    │     智能路由层       │
                    │  (Carrier Router)    │
                    └────┬───────┬────────┘
                         │       │
            ┌────────────┘       └────────────┐
            ▼                                  ▼
  ┌──────────────────┐              ┌──────────────────┐
  │   聚合 API 层     │              │  直连承运商 API   │
  │  (覆盖 900+ 承运商) │           │  (主流 5-10 家)   │
  └──────────────────┘              └──────────────────┘
```

### 1.2 聚合 API（广覆盖）

| 服务商 | 定位 | 免费额度 | 付费起价 | 覆盖承运商 |
|--------|------|----------|----------|-----------|
| **17Track** | 中国市场主力 | 100次/天 | ~$10/月 | 邮政+中国承运商强 |
| **AfterShip** | 国际市场主力 | 100次/月 | $29/月 | 900+ 全球承运商 |
| **TrackingMore** | 性价比备选 | 100次/月 | $15/月 | 900+ 全球承运商 |

**路由策略**：
- 中国发出的包裹（中国邮政、云途、燕文、4PX、递四方等）→ 优先 17Track
- 国际快递（DHL/FedEx/UPS/TNT）→ 优先直连官方 API，降级到 AfterShip
- 其他承运商 → AfterShip 兜底
- 所有查询失败 → TrackingMore 二次兜底

### 1.3 直连承运商 API（高精度）

| 承运商 | API 类型 | 认证方式 | 免费额度 | 数据格式 |
|--------|----------|----------|----------|----------|
| **DHL** | REST | OAuth 2.0 | 需申请商业账号 | JSON |
| **FedEx** | REST | OAuth 2.0 + API Key | 1000次/周 | JSON |
| **UPS** | REST | OAuth Token | 1000次/天 | JSON |
| **TNT** | REST/SOAP | API Key | 需商业合作 | XML/JSON |
| **China Post (EMS)** | 有限 | 合作伙伴制 | 无公开免费 | 用聚合API替代 |

### 1.4 单号自动识别

利用开源库（如 `tracking-number` 1.2K Stars）通过单号格式自动匹配承运商：
- `1Z` 开头 → UPS
- `794` 开头 → FedEx
- `JD` 开头 → 佳达
- 13 位纯数字 → 中国邮政 EMS
- 自定义规则引擎覆盖更多承运商

### 1.5 数据刷新策略

| 包裹状态 | 刷新间隔 | 缓存 TTL |
|----------|----------|----------|
| 待揽收 | 每 2 小时 | 30 分钟 |
| 运输中 | 每 30 分钟 | 5 分钟 |
| 清关中 | 每 15 分钟 | 5 分钟 |
| 派送中 | 每 10 分钟 | 3 分钟 |
| 已签收 | 停止刷新 | 1 小时 |
| 异常/退回 | 每 1 小时 | 15 分钟 |

## 二、数据清洗

### 2.1 统一数据模型

各承运商返回的数据格式差异极大，需要统一为标准 Schema：

```
Shipment（运单）
├── tracking_number    运单号
├── carrier_code       承运商代码
├── carrier_name       承运商名称（中/英）
├── origin             发件地（国家、城市）
├── destination        收件地（国家、城市）
├── current_status     当前状态（标准化枚举）
├── estimated_delivery 预计送达时间
├── actual_delivery    实际送达时间
├── events[]           轨迹事件列表
│   ├── timestamp      事件时间（统一 UTC）
│   ├── location       事件地点
│   ├── country_code   国家代码（ISO 3166）
│   ├── status_code    标准状态码
│   ├── description_zh 中文描述
│   ├── description_en 英文描述
│   └── raw_status     承运商原始状态（保留用于调试）
└── metadata
    ├── data_source    数据来源（17track/aftership/dhl_direct/...）
    ├── last_synced    最后同步时间
    └── confidence     数据可信度评分
```

### 2.2 状态码标准化

将各承运商的状态映射为 10 个标准跨境物流状态：

| 标准状态码 | 中文 | 英文 | DHL | FedEx | UPS | 中国邮政 |
|-----------|------|------|-----|-------|-----|---------|
| `PENDING` | 待揽收 | Pending | - | - | - | 待揽收 |
| `PICKED_UP` | 已揽收 | Picked Up | PU | PICKED_UP | P | 已揽收 |
| `IN_TRANSIT` | 运输中 | In Transit | DF | IN_TRANSIT | D | 运输中 |
| `EXPORT_CUSTOMS` | 出口清关 | Export Customs | - | - | - | 已出口 |
| `IMPORT_CUSTOMS` | 进口清关 | Import Customs | - | HELD_CUSTOMS | - | 清关中 |
| `OUT_FOR_DELIVERY` | 派送中 | Out for Delivery | OD | OUT_FOR_DELIVERY | DP | 派送中 |
| `DELIVERED` | 已签收 | Delivered | DL | DELIVERED | DL | 已签收 |
| `FAILED` | 投递失败 | Delivery Failed | XX | EXCEPTION | X | 异常 |
| `RETURNED` | 已退回 | Returned | RT | RETURNED | R | 已退回 |
| `EXPIRED` | 已过期 | Expired | - | - | - | - |

### 2.3 清洗规则

1. **时间标准化**：所有时间统一转换为 UTC，前端按用户时区展示
2. **地点标准化**：城市名模糊匹配 + GeoNames 数据库校正，标准化为 `城市, 国家` 格式
3. **去重**：同一事件可能从多个数据源获取，按 `时间+地点+状态` 去重
4. **排序**：按时间升序排列，确保轨迹事件的逻辑连贯性
5. **异常检测**：
   - 时间回退（后续事件时间早于前一事件）→ 标记异常
   - 地理位置跳跃（前后两个事件地理距离不合理）→ 标记待确认
   - 长时间无更新（超 15 天无新事件）→ 标记为疑似异常
6. **多语言翻译**：原始描述如果是非中/英文，通过翻译映射表转为中英双语

### 2.4 数据质量评分

每条轨迹自动计算数据可信度（0-100）：
- 来自直连 API → +30 分
- 来自聚合 API → +20 分
- 事件时间完整 → +20 分
- 地点信息完整 → +15 分
- 轨迹逻辑连贯（无回退/跳跃）→ +15 分

### 3.2 查询流程

```
用户输入单号
    │
    ▼
┌──────────────┐
│ 单号格式校验  │ → 格式不合法 → 返回错误提示
└──────┬───────┘
       │ 格式合法
       ▼
┌──────────────┐
│ Redis 缓存查询│ → 命中 → 直接返回结果
└──────┬───────┘
       │ 未命中
       ▼
┌──────────────┐
│ 数据库查询    │ → 命中且未过期 → 返回 + 更新缓存
└──────┬───────┘
       │ 未命中或已过期
       ▼
┌──────────────┐
│ 承运商自动识别│ → 确定承运商代码
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ 智能路由分发  │ → 选择数据源（直连 / 聚合 / 备用）
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ 数据清洗标准化│ → 统一格式 + 状态映射 + 翻译
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ 存储 + 缓存   │ → 写入 PostgreSQL + Redis
└──────┬───────┘
       │
       ▼
   返回结果给用户
```

### 3.3 API 设计

**单号查询**：
```
GET /api/v1/track/{tracking_number}
Query: ?lang=zh&carrier=dhl (可选)
Response: { shipment, events[], carrier_info }
```

**批量查询**：
```
POST /api/v1/track/batch
Body: { tracking_numbers: ["xxx", "yyy", ...] }
Response: { results[], failed[] }
```

**Webhook 订阅**：
```
POST /api/v1/webhooks
Body: { tracking_number, callback_url, events: ["delivered", "exception"] }
```

### 3.4 速率限制与鉴权

- 未登录用户：IP 限流，3次/天
- 免费用户：API Key 限流，10次/天
- Pro 用户：API Key 限流，300次/分钟，50000次/天
- 企业用户：API Key 限流，10000次/分钟，无日限
- 采用 Redis Token Bucket 算法实现

## 七、验证方案

1. **数据来源验证**：用 DHL/FedEx/中国邮政的真实单号，分别测试直连 API 和聚合 API 的数据一致性
2. **数据清洗验证**：对比清洗前后的数据，确保状态映射正确、时间排序正确、去重无遗漏
3. **查询性能验证**：缓存命中时响应 <100ms，未命中时响应 <3s
4. **展示验证**：在桌面/平板/手机三种尺寸下验证 UI 渲染效果
5. **限流验证**：模拟免费/Pro/企业用户的请求频率，确认限流策略生效
6. **端到端测试**：从输入单号到看到完整轨迹的全链路测试（Playwright）
